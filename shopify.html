01 — What is a Design System?

The shared language of a product.

A design system is a set of reusable components, design tokens, and guidelines that ensures every screen in a product looks and behaves consistently — regardless of which team built it. It's the difference between a product that feels designed and one that feels assembled.

Without a design system, every designer makes their own decisions about button sizes, colors, and spacing. The product looks inconsistent. Teams move slowly, solving the same problems over and over. With a design system, you decide once and reuse everywhere.

"Shopify's design system is called Polaris. Every button, every input field, every status badge across the entire Shopify admin — all defined in Polaris. When the design team changes a color token, thousands of UI elements update at once."

01
Tokens — the foundation
Raw values: colors, spacing, typography, shadows. Defined once as variables. Every component references them. Change a token and the entire product updates automatically.
02
Components — the building blocks
Pre-built UI: buttons, inputs, cards, badges, navigation. Each documented with when to use it, when not to, and what variants exist. Built on top of tokens.
03
Patterns — the rules
How to combine components: how to build a form, a table, an empty state. The decisions that stop every team from solving the same problem differently.
How Polaris is structured — bottom to top:
Brand Values — Shopify's mission, voice, principles
Design Tokens — color, type, spacing, shadow, radius
Components — Button, Input, Badge, Card, Nav, Table
Patterns — Forms, Empty States, Tables, Modals
Products — Admin, POS, Checkout
02 — Foundation Tokens

Every design decision
as a variable.

Tokens are the atoms of the system. Instead of hardcoding a hex value into a button, you reference a semantic token — --p-color-bg-interactive. When Shopify updates the brand color, one token change updates every button, every link, every interactive element across the entire product. That's the power of a token-first system.

03 — Component Library

Reusable. Accessible.
Documented.

Every component in Polaris follows three rules: it works in isolation, it composes cleanly with other components, and it ships with guidance on when to use it — and when not to. The "never" rules are as important as the component itself.

Primary
Primary Button
The most important action on a page — Save, Add, Continue. Green background signals the main path forward. One Primary button per section, maximum.
↗ Never use two Primary buttons side by side
Secondary
Secondary Button
For secondary actions like Cancel, View, or Download. Always paired with a Primary button. Appears to the left of the Primary button, never alone.
↗ Never use alone without a Primary nearby
Destructive
Destructive Button
For irreversible actions — delete, remove, revoke. Red signals danger. Always requires a confirmation modal. Never the primary CTA on any page.
↗ Always pair with a confirmation dialog
Plain
Plain Button
For low-priority tertiary actions within text, tables, or compact UI. Lowest visual weight — used when Primary/Secondary would be too heavy.
↗ Use sparingly — never for critical actions
Default
Store name
Text Input — Default
Standard resting state. Label always above, never inside. Placeholder text gives an example, not instructions. Required fields marked with *.
↗ Placeholder is not a label — always use both
Focused
Email address
Text Input — Focused
Green border and a 20% opacity glow on active field. Shows which field is currently being edited. Must meet WCAG 2.1 minimum contrast for accessibility.
↗ Focus ring must be visible at all times
Error
Price *
Enter a valid price — numbers only (e.g. 29.99)
Text Input — Error
Red border + error message directly below. The message tells the user what went wrong AND how to fix it. "Invalid input" is never acceptable.
↗ Error message = what happened + how to fix it
Success
Active
Badge — Success
Positive states: Active, Paid, Fulfilled, Published. Green surface, dark green text. Green is reserved for success — never use it decoratively.
↗ Color carries meaning — never decorative
Warning
Pending
Badge — Warning
States needing attention but not failed: Pending, Partial, At Risk. Amber surface. Something isn't wrong yet but needs a response before it becomes critical.
↗ Warning ≠ error — don't use red for pending
Critical

Badge — Critical
Failed or blocked states: Declined, Failed, Cancelled. Red is strong — reserve it for genuine failures, not incomplete or draft states.
↗ Reserve red for actual failures only

Neutral states: Draft, Archived, Scheduled. Blue surface, no urgency implied. The state is informational — it doesn't require immediate action.
↗ Blue = informational, not interactive

05 — What I Learned

A design system is never finished.

1
Tokens first. Always.
Every time I built a component before establishing its token, I had to rebuild it. The foundation has to come first. A button color isn't just a color — it's a semantic role. Getting that distinction right is the difference between a library and a system.
2
Naming is design.
Calling a token "green" is a style. Calling it "interactive" is a system. The name determines how it gets used across the entire product. A well-named token is self-documenting. A poorly named one gets misused every single time.
3
The "never" rules are as important as the components.
Documentation isn't just "here's how to use this." It's "here's when you must not." Never two primary buttons. Never red for a pending state. Never use placeholder as a label. Those constraints are what make a design system a system — not just a library of parts.
